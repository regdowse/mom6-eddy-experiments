# Beta experiment workflow: read-only audit and proposal

26 November 2026. Planning document; no experiment setup, run or software installation performed.

## Scientific motivation and literature

Reg's objective is to investigate planetary and topographic PV-gradient effects on eddy tilt, beginning with a simple flat-bottom planetary-beta comparison. Later questions include background flow and opposed planetary/topographic gradients. Cancellation of a selected background gradient is a testable hypothesis, not a guarantee of zero tilt: finite-amplitude flow, boundaries, stratification and transient evolution may matter.

[Yang et al. (2020), Ocean Dynamics](https://doi.org/10.1007/s10236-020-01375-3): the publisher's abstract is accessible, but the full published paper is subscription content in the available reader. The abstract reports an MITgcm and analytical study, polarity-dependent vertical structure and up to 30 km tilt at beta = 2.15e-11 m^-1 s^-1 over a flat bottom; stratification, eddy strength and rough topography also matter. The abstract alone does not verify a quantitative monotonic beta sweep.

A distinct, earlier [Yang et al. (2018) discussion preprint](https://os.copernicus.org/preprints/os-2018-39/) is fully accessible; it was not accepted in that journal and should not be treated as the text of the 2020 article. It compares f-plane and beta-plane experiments using the same initial condition in a flat-bottom MITgcm domain, and reports an upright eddy in the f-plane case. Its setup uses open radiation boundaries, 2.5 km horizontal grid spacing, a 2000 m bottom, 28 vertical levels, and an initially strong Northern Hemisphere warm anticyclone, with 50-day integrations. It highlights how stratification affects the vertical distribution of tilt. These differences mean its reported distances are context, not acceptance thresholds for our Southern Hemisphere MOM6 configuration. The archived MOM6 `wd` is diapycnal velocity, not the physical vertical velocity discussed in the preprint.

## What is actually in the reference

- `MOM_input` uses Cartesian 100 x 100 cells over 500 km x 500 km, with `REENTRANT_X=False` and `REENTRANT_Y=False`; the initializer explicitly expects closed, nonperiodic boundaries. The current and archived `ocean_static.nc`/input topography indicate wet depths of about 35.7–4000 m, not a flat bottom. The central flat region and slope influence through time still need scientific assessment. The proposed larger-domain baseline requires compatible reference grid and initialisation; editing beta alone is insufficient.
- Current settings are `ROTATION="betaplane"`, `F_0=-1e-4 s^-1`, `BETA=2e-11 m^-1 s^-1`. Archived effective `BETA_LAT_REF=0 m`; domain centre y = 250,000 m. The initializer uses `f(y)=F_0+BETA*(y-BETA_LAT_REF)`, so centre f = -9.5e-5 s^-1 in the present configuration. Holding F_0 and the reference latitude fixed while changing beta changes centre f and, through the initializer, SSH/interface displacement. For an experiment isolating gradient strength at fixed centre f, specify an explicit common reference at the eddy centre or calculate F_0 for each beta. The latter changes two control values but maintains the intended physical constant. Confirm MOM6 effective settings and initial validation in a pilot.
- `initialisation/generate_initial_state.py` reads the effective `F_0`, `BETA` and `BETA_LAT_REF`, computes the local centre f and constructs the initial SSH and isopycnal interface geometry using it. It records beta, F_0, centre f, configuration YAML and build information in the NetCDF and validates geostrophic residuals using spatially varying f. Even when a centre-f convention makes dynamical initial fields match, the beta-dependent metadata and balance checks differ; whether to use a common identical IC or separately generated ICs is a scientific design decision to document and validate. Do not assume changing `MOM_input` automatically regenerates files.
- With fixed centre f the center-f approximation may allow the same state fields across beta settings, but nonzero-beta balance remains approximate and initial adjustment can differ. The initializer expects saved reference geometry to match `topog.nc` and the grid, so any flat-bottom design must address both rather than silently substituting a file.
- The actual archived run is UUID `61093f28-a770-445d-a96d-7fc4f2ff0eec`, `archive/output000`, 31 daily records and approximately 1.4 GiB of output files. Archived MOM_input and diag_table differ from current files: the former fixes comment markers; the latter removes a geothermal request and changes the SSH output request. The archived manifest records initial_state MD5 `b132aa6ded1e663a3c69731f8cccfa1f`, whereas the current same-path input has MD5 `a1e3b65492e362b90da5078037edcb08`. A changed checksum establishes different bytes, not necessarily different physical fields. The archived input manifest retains its old path and hash, not necessarily a preserved copy at that path; recover the exact run input or establish its availability before claiming reproducibility. MOM_IC.nc may aid investigation, but has not been established as a byte-identical replacement.
- Existing run manifests record hashes for the inputs and executable; archive/output000 also preserves controls, effective model parameter documentation and environment data. Current NetCDF inputs and the executable are at absolute external paths, and the experiment is a subdirectory of the broader PhD Git repository; `input/` NetCDF files are not tracked in that repository. `build_versions.json` records source revisions, but a matching binary/build still needs verification. Explicit storage/retention and provenance are necessary.

## ACCESS tool findings

The [generator](https://github.com/ACCESS-NRI/access-experiment-generator) describes creating a control and perturbation branches from a repository revision and changing configuration values via YAML; its source contains a MOM6-input updater. The [runner](https://github.com/ACCESS-NRI/access-experiment-runner) describes coordinating branch-based Payu runs and supports cold or restart starting points. Chris's supplied example uses `model_type: mom6`; the main-branch YAML guide's supported-model list omits it, so actual version and mom6-solo compatibility must be checked, rather than inferred from either source alone.

The documented `/g/data/vk83/prerelease/modules` path was not visible in this execution environment (`/g/data/vk83` absent), so installed `payu/dev`, generator and runner versions could not be confirmed. This may reflect the current host or filesystem mounts; it does not establish that they are unavailable on Gadi. No installation or tool execution was attempted.

The current generator expects a cloneable configuration repository with paths relative to its root, whereas the candidate is a subdirectory of a broader repository and uses absolute local input/executable paths. Assess a dedicated configuration repository or another compatible arrangement before generating branches; do not assume cloning the present top-level project will directly work.

## Proposed pilot workflow — discussion, not approved implementation

1. Agree a flat-bottom baseline, fixed centre f, beta values, initial-condition policy, run length and outputs. Preserve the current sandbox as reference. Check boundary effects and domain size, as well as f-plane symmetry, initialization adjustment, layer thickness, energy and budget quality. No exact-zero tilt or monotonic response is assumed as an unconditional result.
2. Freeze a reviewable baseline configuration at a known commit, with generation code and settings, model build identification, documented external input locations and checksums. Keep large generated files in stable, retained storage; record their hashes and generation/validation reports. Decide whether run inputs should be copied or immutable and how retention is guaranteed.
3. A versioned generator plan defines control and named beta variants. Each branch records the requested `BETA` and, if needed, reference setting or adjusted `F_0`, with an independent cold start and unique Payu identity for each independent experiment. Branch names are convenient labels; the commit and run UUID identify the exact run. Specify values only after scientific agreement.
4. Prepare and validate correct ICs for each branch under an explicit common-IC or per-branch policy, in separate non-overwriting input locations. Record IC checksums and validation, including centre f and beta-dependent imbalance. Avoid assuming generator YAML creates or validates NetCDF files.
5. Pilot two cases (zero beta and one agreed nonzero beta) first. Compare generated branch diffs and the effective archived MOM parameters and Coriolis fields against the plan, verify different UUIDs and correct cold starts, input hashes and archive paths. Then use the runner for a small sweep if compatible. A branch may be updated after running, so bind each output to the actual commit and archived controls, not branch name alone.
6. Maintain a lightweight run index mapping human-readable experiment name, beta, centre f, branch/commit, IC and executable checksums, UUID, run status and output/archive path. Preserve the generator plan, tool versions, Payu manifests, archived control files, effective parameters and analysis version. Plan output/storage needs and lifetime before expanding; 1.4 GiB/month per run is only a rough estimate from the existing output000 and may change.

Open choices: fixed centre f value (the current value is -9.5e-5 s^-1), common versus independently regenerated ICs, bathymetry and closed-wall design, acceptable baseline adjustment and run length, where to host configurations and long-lived inputs/archives, available modules on the execution host, and the first agreed beta values. These should be settled with Reg before implementation.
